## Money, time and reporting invariants

- Persist positive integer paise as PostgreSQL BIGINT; the future SQLite projection will use checked INTEGER values. Public money fields are base-10 integer strings (`"129900"` = INR 1,299.00) to avoid JSON BigInt/float ambiguity. The enforced maximum per amount is `999999999999` paise; reject zero except budget/allocation limits, which may be zero. Refund/allocation aggregates are checked against their parent amounts; a goal's live contribution sum is bounded by the same maximum while still permitting overfunding relative to its target. Services use BigInt arithmetic; PostgreSQL reporting returns SUM values as decimal text. Aggregate reports can exceed the per-record maximum and remain exact integer strings.
- Store `currency = INR`, not an implicit currency. SQL CHECKs enforce INR on users, transactions, monthly budgets and savings goals; allocations and contributions inherit their parent's monetary context. No float arithmetic or silent multi-currency totals. Decimal-entry parsing with at most two fractional digits belongs to the client; REST accepts integer paise strings.
- Transaction `occurredAt` and contribution `contributedAt` require offset-qualified API timestamps and are stored as `timestamptz(3)`. The original entered offset is not stored separately. Reporting uses the user's IANA `timezone`; defaults are `Asia/Kolkata`, `en-IN` and INR. Creation/update timestamps are server-generated. Budget `month` is a DATE on the first day; goal `targetDate` is an optional local DATE. API representations use `YYYY-MM` and `YYYY-MM-DD` respectively. Month reports use half-open local-month bounds converted to UTC, never device timezone guesses.
- Positive amounts and explicit `EXPENSE`, `INCOME`, `REFUND` kinds; no negative income masquerading as a refund. A refund requires an owned live expense, must use that expense's category, and is independently dated. Its original category may be archived; new expenses/income require an active category of the matching kind. Sum of live linked refunds cannot exceed expense amount. Phase 4 serializes refund create/update/delete and expense edit/delete under the user's `SyncState` row lock, then validates the combined state. Reducing the expense below its refunded sum or changing its category while live refunds exist is rejected. Delete linked refunds first before deleting their expense. Transaction type is immutable through REST; original expense links cannot be reassigned.
- Gross expense = expense sum; refunds = refund sum; net expense = gross minus refunds; surplus = income minus net expense. Budgets use net expenses in the period, including refunds for older purchases. Show gross/refund/net separately in analytics. Goal contributions are earmarking records and never counted as expenses or deducted again from surplus. No claim that surplus is an actual account balance.

## Entity catalogue

All owned mutable financial entities have UUID `id`, `userId`, `createdAt`, `updatedAt`, integer `version` starting at 1, and nullable `deletedAt`. Transaction, budget, allocation, goal and contribution creates require a client UUID; category creates may supply one or use a generated UUID. This prepares identities for later sync without implementing offline writes. Ownership, version, timestamps and source metadata are never writable by clients. Deletes retain the row and its identity, increment its version and return a minimal `{id, version, deletedAt}` tombstone. Transaction descriptions/payees and contribution notes are cleared on deletion; deleted goal names become a fixed placeholder. Soft-deleted IDs cannot be reused.

## Relationships and ownership

```text
User 1--N Session 1--N RefreshCredential
User 1--N AccountToken
User 1--N Category 1--N Transaction
Transaction(EXPENSE) 1--N Transaction(REFUND)
User 1--N MonthlyBudget 1--N CategoryBudget N--1 Category
User 1--N SavingsGoal 1--N GoalContribution
User 1--1 SyncState; User 1--N ChangeEvent / MutationReceipt / AlertDelivery
```

Owned referenced financial entities have `(userId, id)` unique keys. Composite foreign keys enforce same-owner category, goal, budget and original expense links, with `ON DELETE RESTRICT` and `ON UPDATE NO ACTION`. Services also scope reads, updates, filters and nested child routes to the authenticated owner and live parent; foreign or absent references return 404. Database foreign keys establish ownership/existence but do not establish that a referenced row is live, unarchived, or of the right kind. These checks, refund caps and allocation sums run in services within the mutation transaction. The schema has no PostgreSQL row-level security policy or cross-row sum trigger; direct SQL writes must not bypass the service boundary.

Each user receives `SyncState` and 16 owned default categories atomically at registration, with deterministic per-user default keys and initial category change events. Expenses: Food, Groceries, Shopping, Transportation, Entertainment, Bills, Health, Education, Travel, Subscriptions, Other. Income: Salary, Freelance, Investments, Gifts, Other. This avoids mixing globally writable categories with tenant-owned data. Default keys are unique per user; users can rename/archive defaults. Custom names are trimmed, NFKC-normalized and lowercased for uniqueness. The ordinary unique index on `(userId, kind, normalizedName)` applies to all stored rows, including archived and soft-deleted rows. Recreating an archived name requires restoring the existing category or using a distinct name.

Account deletion currently marks the user `DELETION_PENDING`, revokes sessions, consumes outstanding account tokens and queues an `ACCOUNT_DELETE` job. Physical purge and its retention/backup policy remain future work; there is no automatic database cascade deleting the financial ledger.

## Budget and savings semantics

Monthly budget is a limit, not an account balance. Category limits are allocations within the overall budget; their sum must not exceed the monthly limit. In Phase 4 the per-user mutation lock serializes both overall-limit edits and allocation create/edit/delete; services re-read the live parent and enforce the combined limit. Allocation edits/deletes check the allocation's `baseVersion`, while overall edits/deletes check the budget's version. Allocation changes do not increment the unchanged parent's version. Deleting a budget atomically soft-deletes its live allocations and emits a tombstone event for every changed row. A new ID may subsequently create a budget for the deleted month. No automatic rollover. Copying a month is an explicit later convenience. Historical limits remain editable with version checks and change events; the UI must distinguish reporting month from modification time.

Savings progress is the sum of live contributions, may exceed the target within the supported aggregate bound and must never be added to income. Display overfunding accurately. Goal target reduction can complete a goal; completion is derived, not a second mutable balance. Archive/restore retains the goal ID. Archived goals reject new contributions while existing contributions remain correctable/removable. Deleting a goal with live contributions requires explicit confirmation and atomically soft-deletes those contributions with corresponding change events. Contribution mutations require the exact owned live goal, even if the child ID belongs to another goal of the same owner. Local milestone reaction deduplication remains client work.

Budget detail derives gross expense/refunds/net expense, remaining limit, progress and near/over-limit flags for the user's local month. Dashboard alerts are derived on read at 80%/over-limit thresholds for the overall budget and category allocations. These reads do not queue delivery jobs or insert `AlertDelivery` rows. Durable budget-alert delivery, deduplication and scheduling remain future work. A refund-heavy period can have negative net expense; zero budgets are distinct from unset budgets, and neither budget availability nor surplus is a bank balance.

## Atomic writes, receipts and change events

Every public financial mutation uses `core/database.ts`'s `mutate` wrapper. After authentication and request schema validation, it requires a UUID `Idempotency-Key`, locks the owner's `SyncState` row with `SELECT ... FOR UPDATE`, and verifies that the user is ACTIVE. This lock serializes all financial writes for that user, including refund and allocation races. Financial edits/deletes require `baseVersion`; a mismatch returns 409 with the current owned record/version.

The receipt's request hash covers the canonicalized HTTP method, path, query and body. A prior receipt with the same hash returns its stored HTTP status and JSON body before re-evaluating business rules. Reusing the key for different content returns `409 IDEMPOTENCY_KEY_REUSED`. Receipt lookup is scoped to `(userId, operationId)`.

Domain changes run after a savepoint. A successful operation commits its row updates, all emitted change events and its canonical response receipt together. A handled domain error (including 404, 409 and 422) rolls back to the savepoint, then commits only the error receipt; retrying that key returns the original failure even if intervening edits would now allow the operation. Schema/parameter validation failures outside `mutate` do not consume a key. Unexpected failures roll back the transaction without storing a success receipt. Prisma serialization/deadlock error `P2034` receives at most three transaction attempts; statement, lock and transaction waits are bounded.

Each `emit` increments the locked user's BIGINT `lastSequence` and inserts one `ChangeEvent` with the same sequence, entity ID/version, operation and canonical JSON payload. Entity types are `Category`, `Transaction`, `MonthlyBudget`, `CategoryBudget`, `SavingsGoal` and `GoalContribution`; deletes emit the versioned soft-deleted row. Cascades emit every changed child as well as the parent. Events are application-append-only; the migration does not install a trigger enforcing payload immutability. Phase 6 exposes the transaction/category subset through authenticated sync endpoints; other event types advance the cursor but are not cached offline.

## Indexes, constraints and migrations

- The initial migration enforces positive financial versions; positive, bounded transaction/goal/contribution money; nonnegative, bounded budget/allocation limits; INR; finite timestamps and first-of-month budget dates. It checks transaction type/payment/source values, refund link shape (including no self-link), category kinds/name bounds, transaction text bounds, goal names and contribution note bounds. Enums are stored as strings with SQL CHECKs where specified, rather than PostgreSQL enum types. Approved icon/colour asset keys are enforced by shared REST schemas; there are no SQL asset-key CHECKs.
- User checks cover normalized email, positive profile version, display-name bounds, locale/theme and ACTIVE/DELETION_PENDING status. Unique indexes cover email, hashed refresh/account tokens, category names/default keys, job dedupe keys and alert dedupe keys. Further CHECKs cover account-token purposes, positive change sequence/version with UPSERT/DELETE operations, receipt status 200–499, and job attempts/status (`PENDING`, `RETRY`, `DELIVERED`, `FAILED`, `CANCELLED`). Account-email job payloads are encrypted; the mail worker redacts completed/cancelled payloads. The generic job table does not itself encrypt all job types.
- Transaction indexes cover `(userId, occurredAt, id)`, `(userId, categoryId, occurredAt, id)`, `(userId, type, occurredAt, id)` and `(userId, originalExpenseId)`. An additional partial live index is `(userId, occurredAt DESC, id DESC) WHERE deletedAt IS NULL`. The category/type indexes currently include deleted rows. Reverse scans support ascending/descending order where applicable. Add amount/merchant indexes only after measured query plans.
- Partial unique indexes enforce one live overall budget per `(userId, month)` and one live allocation per `(userId, monthlyBudgetId, categoryId)`. Other indexes cover budgets by owner/month, allocations by owner/parent or owner/category, goals by owner/creation/ID, contributions by owner/goal/date/ID, sessions/credentials and pending jobs. Change-event and mutation-receipt composite primary keys provide their owner/sequence and owner/operation access paths.
- Search uses parameterized case-insensitive merchant/description predicates with bounded query text. REST pagination uses signed owner/path/filter/sort-bound offset cursors, database `skip`/`take`, deterministic ordering with an ID tie-breaker, default limit 25, maximum 100 and maximum offset 100000. Lists can change between pages; they are not frozen snapshots or sync cursors. PostgreSQL trigram indexes remain a measured future option.
- Refund type/category compatibility, live/archived reference rules, cumulative refund/allocation/contribution bounds, parent route membership and optimistic version checks are service invariants. Every future writer must acquire the same user lock and use this mutation/event boundary. If additional parent/child row locks are introduced, preserve the architecture's order: user SyncState, parent records, then children. Never depend on UI checks alone.
- Real-Postgres HTTP tests are authored in `apps/backend/tests/finance.test.ts` with unique users and no truncation/purge. They cover ownership, strict input/money validation, versions, successful and business-error receipt replay after intervening state changes, concurrent refund/allocation/expense edits, archive restoration, cascaded events and direct SQL money/month/ownership constraints. Run them against the dedicated `nivvi_test` database after migration; compilation and test source alone are not evidence that PostgreSQL constraints or races passed.
- Version all PostgreSQL migrations and the future SQLite migrations; verify fresh installs and upgrades with realistic rows. Destructive changes require backup and a reviewed forward/restore plan. No database reset as a migration shortcut.

## Phase 6 sync and local storage

The backend now provides authenticated `GET /sync/bootstrap` and `GET /sync/pull`. Bootstrap pages are capped at 100 transactions and use a signed user-bound keyset cursor plus a fixed change-sequence watermark. Pull pages are capped at 100; client cursors are PostgreSQL BIGINT decimal strings. The mobile client pushes through existing transaction REST mutations with `Idempotency-Key`, row versions and business rules. There is no bulk push route, event pruning, cursor expiry/reset protocol or database migration for Phase 6.

Android uses SQLCipher SQLite with account-scoped `local_profile`, `local_category`, `local_transaction`, `outbox` and `sync_cursor` tables. The random database key is held in SecureStore. A native open checks for `cipher_version` and fails closed if unavailable. Outbox rows retain operation ID, entity, method/path, exact JSON body, base version, attempts, retry time and status. Local projection changes and enqueue happen atomically. Conflict resolution is explicit; edits use a new operation key after rebasing against a returned current version. All amounts remain exact paise strings on the server and checked-safe integer paise per transaction on mobile.

Categories and transactions are cached; only transactions/refunds are offline writable. Budgets/goals remain online-only. Bootstrap event retention is currently indefinite, which allows cursors to remain valid but requires a future retention/reset design before pruning. Expo background work is scheduled at a 15-minute minimum and is OS-deferred; foreground and connectivity recovery are the primary triggers. Device process-death, encryption runtime and multi-device conflict checks remain acceptance requirements in [Phase 6 review](PHASE_6_REVIEW.md).

The Android widget remains Phase 7 work and will need a separate private native inbox and projection store, scoped by account generation. It must distinguish locally saved from server-synced transactions.

Change-event payloads contain financial data: restrict access, redact logs and establish expiry before production. The proposed 180-day log retention and account-lifetime dedupe receipts require storage/privacy review; Phase 4 has no event/receipt expiry or purge worker. Old event and receipt payloads can still contain text removed from the current soft-deleted row. Purged entities must retain minimal non-reusable identity markers until the supported replay window is safely closed. Backups need a separately documented retention policy; soft deletion is not a promise of immediate physical erasure.
