# REST API design and implementation status

## Phase 5 additions — 2026-11-11

Mobile integration uses the existing routes below and adds atomic `PUT /api/v1/budget-plans/:month`. The body is `{baseVersion: number|null, limitMinor: string, baseAllocations: [{id,version}], allocations: [{categoryId,limitMinor}]}`. Both arrays cap at 100. Null parent version requires no live plan for that owner/month. Updates require the exact parent version and complete live allocation ID/version set, including allocations being removed. Duplicate category entries, wrong-owner/kind references and allocation sums above the overall limit fail without partial changes. The whole parent/children/event/receipt write is one transaction. Success is 201 for creation or 200 for replacement, with the budget and allocations in `{data}`. Every call requires a UUID Idempotency-Key; a recorded result replays normally.

Transaction lists additionally accept optional `originalExpenseId` (UUID), always under the authenticated owner's scope. The mobile detail/editor uses it to fetch complete linked refunds rather than assuming history pages are complete. The original CRUD routes remain supported. See [Phase 5 review](PHASE_5_REVIEW.md) for client session/draft/query behavior and actual validation.

## Phase 4 implementation inventory — 2026-11-11

This section records the current source implementation, not test results or deployment verification. It takes precedence over the original Phase 0 proposal retained below. Runtime request contracts are in [`packages/contracts/src/index.ts`](../packages/contracts/src/index.ts), the mounted routes are in [`apps/backend/src/app.ts`](../apps/backend/src/app.ts), and operational commands are in the [backend guide](../apps/backend/README.md).

API paths below are relative to `/api/v1`. Public `GET /health/live`, `GET /health/ready`, and `GET /openapi.json` are at the server root. OpenAPI 3.1 is generated by `makeOpenApi()` using the explicit route inventory maintained in `src/openapi.ts` and shared Zod input schemas. OpenAPI's default server is `/api/v1`; the three root operations override it to `/`.

### Phase 6 sync endpoints

`GET /sync/bootstrap?limit=50&cursor=...` returns categories on the first page, up to 100 current transactions, a fixed per-user sequence watermark, and a signed owner-bound keyset cursor. Continue until `cursor` is null. Then call `GET /sync/pull?cursor=<decimal sequence>&limit=50`; event pages contain full versioned entity payloads, a high-water mark and `nextCursor`. Both endpoints require bearer authentication and reject unknown query fields. Client storage scopes every cached row and cursor by the authenticated user. Event pruning is not implemented, so sync cursors currently have no expiry/reset response.

### Current transport, validation and mutation rules

- JSON success is `{data: ...}`; paginated responses add `page: {nextCursor, hasMore}`. Categories return an array in `data`. Financial deletion returns `{data:{id,version,deletedAt}}`. `/openapi.json` returns the plain specification object. API errors use `{error:{code,message,...details},requestId}` and `X-Request-Id` is returned on responses.
- UUID paths/operation keys, strict request objects and strict declared query schemas prevent writable ownership/source/version metadata. Unknown query names and repeated scalar parameters on routes with a query validator return 400; routes without a query validator do not promise this check. OpenAPI lists individual query parameters and links the complete validator through `x-query-schema`.
- Public money inputs are positive integer paise strings up to `999999999999`; budget limits may be `"0"`. Currency is INR. Report aggregates use exact integer strings and can exceed the per-record input ceiling; signed net expense/surplus/availability are valid. Per-goal contribution totals are capped at the supported input ceiling. Budget `progressBasisPoints` is a signed integer string or null for a zero limit; `10000` basis points means 100%.
- Every financial create/edit/delete uses a per-user transactional lock, atomic receipt and change events, including cascades. The operation key is user-scoped and bound to canonical method, path, query and body. Identical retries replay the original status/body, including recorded business errors; changing the request with the same key returns 409 `IDEMPOTENCY_KEY_REUSED`. Validation/authentication failures before mutation are not recorded receipts.
- Patches require body `baseVersion`; deletes require query `baseVersion`. Missing/invalid versions return 400; stale versions return 409 `VERSION_CONFLICT`, with `currentVersion` and, for financial conflicts, owned `entityId`/`current` when supplied. Use a new operation key for a corrected request. Profile patches compare `baseVersion` to `profileVersion` and do not use financial idempotency.
- Paginated lists default to 25, cap at 100 and use deterministic sorting with ID tie-breakers. Signed cursors bind the user, route/scope, filters, sort and supplied query context; accepted offsets cap at 100000. Preserve the original query when following a cursor. Lists are live, not frozen exports or synchronization streams.
- Datetimes require explicit ISO offsets. Transaction list `from`/`to` are optional, half-open, and when both supplied must increase within 3660 elapsed days. Budget month ranges are optional, half-open and increasing when both supplied, without a separate span cap. Analytics `from`/`to` are both required, half-open, increasing and capped at 366 elapsed days. Invalid report spans return 422 `INVALID_REPORT_WINDOW`; malformed schemas return 400.
- Request JSON is capped at 64 KB. Outside test mode, process-memory rate limiters apply a global 1000 requests/15 minutes and a shared auth-prefix 30 requests/15 minutes; auth router IP protection is 100/15 minutes and applicable auth/account identities are 10/15 minutes per route. They return 429. These counters are process-local; they do not provide distributed quotas. Test mode skips these limiters.
- Access tokens are HS256 JWTs with a 600-second lifetime, issuer `nivvi-api`, audience `nivvi-mobile`; each request checks the live session and ACTIVE account. Refresh families expire 30 days after session creation without sliding extension. Reset/verification tokens expire after 15 minutes, are single-use, and replace previous outstanding tokens of the same purpose. Current financial routes do not require verified email.
- Implemented status families include 201 create; 200 reads/edits/deletes; 202 queued account actions; 400 validation/cursor/key failures; 401 authentication failures; 404 absent/foreign records; 409 version/business conflicts; 413 body size; 422 semantic failures; 429 rate limits; 500 generic failures; and 503 readiness/transient retry failures. There is no implemented sync-expiry 410 contract yet.

### Reporting semantics and current boundaries

PostgreSQL performs user-scoped, live-record aggregation. Each analytics/dashboard response uses a repeatable-read database transaction for its totals and breakdowns. Month windows use the authenticated user's current IANA timezone. Daily/weekly/monthly buckets use local calendar boundaries; weeks start Monday. Bucket `from`/`to` include UTC offsets, including DST changes. Only nonempty buckets are returned; their full calendar boundaries can extend outside the request, but amounts include only records inside the requested window. `groupBy` affects summary buckets; category/merchant endpoints accept the shared report query but retain their category/merchant grouping. Grouped outputs have no pagination or separate group-count cap; the reporting time window bounds their source rows.

`grossExpense = expenses`, `refunds = refunds dated in the window`, `netExpense = grossExpense - refunds`, `surplus = income - netExpense`. Refunds for older purchases can make current period/category net expense negative. Category denominator is the period's net expense, not a positive-only pie denominator. Missing merchants are a null key with label `Unspecified`; nonblank merchant names are trimmed for grouping, with spelling/case otherwise preserved. Goal contributions never count as income/expenses and do not reduce surplus. Surplus and budget availability are not bank balances or confirmed savings.

Comparison `absolute` is current minus baseline paise. `percentage` is a decimal string computed as `(current-baseline)/abs(baseline)*100`, truncated toward zero to two places; a zero baseline yields null. Dashboard `budget` and `availableBudgetMinor` are null when unset; a zero budget is distinct. Dashboard goals count live, unarchived goals and sum lifetime live contributions, including amounts outside the selected month. Recent records are confined to the selected month and capped at five. Alerts are derived in-app: near limit at >=80% for a positive limit, over limit above 100% (including positive spending against zero). They do not represent push/email notification delivery.

Current operational boundaries: account deletion sets `DELETION_PENDING`, revokes sessions/account tokens and queues `ACCOUNT_DELETE`; no purge consumer or deletion-completion guarantee exists. Account mail is queued separately; local file mail writes development artifacts and sends no email, while SMTP transport and actual delivery require independent verification. The mail command handles at most one eligible account-mail job per invocation. Phase 6 adds the native mobile sync client; see [Phase 6 review](PHASE_6_REVIEW.md) for test evidence and remaining runtime checks.

## Original Phase 0 proposal (design context)

The following proposal is retained for design history and future work. For current behavior, use the dated Phase 4 inventory and generated OpenAPI above. References below to widget/sync/local behavior describe planned integrations. Deployments should terminate TLS before this HTTP application.

## Transport conventions

- UUID entity/operation identifiers. Money: positive base-10 paise strings with currency INR; versions: positive integers; date-times: ISO 8601 with explicit offset; month: `YYYY-MM`; reporting timezone: IANA name.
- Success: `{ "data": ... }`. Lists additionally return `page: { nextCursor, hasMore }`. Errors: `{ "error": { "code", "message", "fieldErrors"? }, "requestId" }`; never return tokens, stack traces or raw SQL in errors.
- Default page size 25, maximum 100; deterministic sort with ID tie-breaker. Validate every query parameter, reject unknown writable fields and bound strings/request bodies. Invalid bodies cannot mass-assign owner/version/source metadata.
- Every financial create/edit/delete requires `Idempotency-Key` containing the operation UUID. Edits/deletes supply `baseVersion` (delete via required version query parameter). Server stores a request hash and canonical response atomically. Identical retry returns its original outcome; key reuse with different content returns `409 IDEMPOTENCY_KEY_REUSED`.
- Use 201 create, 200 reads/updates/idempotent deletes (delete returns tombstone), 400 malformed request, 401 expired/invalid authentication, 403 insufficient account privilege, 404 absent or foreign entity, 409 version/business conflict, 410 expired sync cursor, 422 semantic validation failure, 429 rate limit with Retry-After, 500 generic unexpected error. Client code uses machine codes, not translated message matching.
- Rate limits by route, account and IP; explicit auth/reset protections, bounded pagination/date spans and sync batches (initial cap 50). CORS is not mobile authentication. Future browser auth requires a separate reviewed cookie/CSRF policy.

## Synchronisation (Phase 6)

| Method | Route | Contract |
| ------ | ----- | -------- |
| GET | `/sync/bootstrap?limit=&cursor=` | Categories on the first page, up to 100 current transactions, fixed sequence watermark, signed owner-bound keyset cursor and `hasMore`. |
| GET | `/sync/pull?cursor=&limit=` | Up to 100 ordered change events, decimal-string `nextCursor`, `highWater` and `hasMore`. |

Both routes require bearer authentication, reject unknown query keys and return the standard `{data}` envelope. The mobile client pushes local operations through existing transaction POST/PATCH/DELETE routes, each with a stable UUID `Idempotency-Key`; there is no bulk `/sync/push` route. Bootstrap uses a repeatable-read transaction for each bounded page. The first page captures the sequence watermark; later pages carry it in a signed cursor bound to the user. Mutations after the watermark are reconciled by pull. Event sequence allocation is serialized with each account's financial writes.

The client advances its sequence only after applying a pull page locally. Event pruning and cursor expiry are not implemented, so the service currently has no `410 SYNC_RESET_REQUIRED` response. Do not remove old change events until reset/reconciliation semantics are added.

Example conflict shape (illustrative contract, not fabricated live data):

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "This transaction changed on another device.",
    "currentVersion": 4,
    "entityId": "<owned-transaction-uuid>",
    "current": "<canonical record or tombstone>"
  },
  "requestId": "<request-id>"
}
```

## Health and verification

`GET /health/live` reports process liveness; `GET /health/ready` currently checks PostgreSQL with configured database timeouts. Neither exposes credentials, hostnames or detailed database errors publicly. `GET /openapi.json` now documents the implemented schemas, auth, pagination and errors. The original proposal and source inventory are not proof of successful runtime verification.

Required tests include foreign IDs in reads/writes/filters/linked entities, reset and refresh replay, duplicate mutation keys, invalid money, refund races, budget allocation races, invalid date windows, version conflicts, migration constraints and sync cursor/account isolation. See [Phase 6 review](PHASE_6_REVIEW.md) for the current PostgreSQL suite and remaining offline process-death checks.
